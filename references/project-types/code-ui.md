# 维度定义 · 代码 / UI 项目（type: code-ui）

> 本文件只定义**前缀与字段含义**，不定义技术实现。前缀空间可与其它类型共享。

| 前缀 | 维度 | 什么东西算一个 | 字段提示 |
|---|---|---|---|
| `MOD` | 功能模块 | 一组内聚能力的边界（目录级） | 职责句写"提供什么能力" |
| `UI` | 界面组件 / 界面件 | 用户能看到的**一块**：组件、弹层、卡片、表单、导航件 | 别名最多——用户口头称呼最杂，重点维护 |
| `PG` | 页面 / 路由 | 一个可寻址的整体视图 | 依赖填它主要由哪些 `UI-` 组成 |
| `API` | 接口 / 数据契约 | 一个对外契约（端点 / 函数签名 / 事件） | 状态改了要同步影响面 |
| `ST` | 状态 / 数据流 | 一块共享状态或一个数据流（store、context、管道） | 循环依赖高发区，警惕 |
| `DM` | 数据模型 | 一个持久化实体或类型定义 | 变更常牵动 API 与 UI |
| `AST` | 静态资产 | 图片、图标、字体、音效、视频 | 位置可填目录 |
| `VIS` | 视觉设计件 | 走 `design-workflow` 产出的设计稿 / 视觉规范 | 与 `AST` 的区别：VIS 是"设计决策载体"，AST 是"落地产物" |

## 常见命名陷阱（本类型特有）

- **UI 与 PG 混淆**：一个组件被当成页面登记 → 判据：它有没有自己的路由/能不能独立寻址。
- **MOD 泛化**："用户模块"这种名字通不过命名三问，要能说出"提供什么能力"。
- **ST 隐形**：共享状态常常没人登记，等出现"这个数据到底从哪来的"时已经晚了 → 只要有两个以上消费者，就登记。
- **一个文件多职责**：一个文件塞了三件事，仍按**职责**拆三条注册，位置都指向同一文件，并在备注标「待拆」进开环。

## 依赖写法

`依赖` 列写 ID：`UI-012 依赖 API-003, ST-002`。
`UI → API → DM` 是最常见方向；出现 `DM → UI` 或环 → 边界划错，写决策卡。
