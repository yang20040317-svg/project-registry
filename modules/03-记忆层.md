# 03 ｜ 记忆层（引擎 B）

**上一步输入**：02 的资产 ID 空间。
**本步要做**：让"上次为什么这么定、上次聊到哪"在任何一次新会话里都能恢复。
**输出给**：下一次开工的上下文包。

---

## 一、三层记忆

| 层 | 载体 | 粒度 | 谁读 |
|---|---|---|---|
| **L1 会话记忆** | `memory/sessions/YYYY-MM-DD-<slug>.md` | 一次对话 | 下次开工快速接上 |
| **L2 决策记忆** | `memory/decisions/ADR-001-<slug>.md` | 一个选择 | 被质疑/被推翻时 |
| **L3 项目记忆** | `memory/context-packet.md` | 项目当前态 | **每次开工第一读** |

外加 **开环** `memory/open-loops.md`：未闭环事项。它是三层之外的"未完成队列"，也是上下文包最有价值的一段。

---

## 二、L3 上下文包（开工第一读，可脚本生成）

固定六段，顺序不可改。`registry.py context` 自动从注册表 + 近期会话 + 生效决策生成，不手抄。

```markdown
# 上下文包 · <项目名> · 2026-09-24

## 1 项目是什么
（来自 PROJECT.md 的一句话定位 + 边界）

## 2 现在到哪
（当前阶段 + 最近 3 次会话的一句话结论）

## 3 活跃资产
（状态为 在建/可用 的资产，**按「更新」列倒序**取最近 10 条：ID · 语义名 · 状态 · 位置）

## 4 近期决策
（最近 5 条生效中的 ADR：ID · 一句话决定 · 影响资产）

## 5 开环与阻塞
（open-loops.md 的**表格部分**，不含 H1；**按阻塞程度排序**：卡住具体资产的排最前，其次有卡点的，同档按登记日早的优先）

## 6 建议起步点
（由开环 + 在建资产推导：下一步最该做什么）
```

**纪律**：上下文包是**生成物不是手写物**。手写会腐化——手抄三次就没人再更新它了。

**占位符不当真值输出**：PROJECT.md 里没填的字段（`- 一句话定位：（给谁、解决什么）` 这类）会被识别为占位符，上下文包里写成"（还没填）"，不会把空话当成项目定位一本正经地念出来。

**不分档**：L 档的会话写在 `memory/log.md` 里，`context`（以及 `close`）会按 `# ` 切块读它，照样生成上下文包。小项目恰恰最需要"开工第一读"，不能因为档位轻就让 L3 记忆空转。

**「最近」的口径（四处一致）**：活跃资产表、构思表、第 6 段建议起步点、第 4 段近期决策，一律按**日期优先、同一天按 ID 序号倒序**取最近。次级依据不可省——「更新」列写到月-日（`09-25`）为止，同一天登记的一批这个值完全相同，Python 排序稳定、`reverse=True` 在键相等时等于没执行，只按日期排会稳定地给出当天**最先**登记那批，而表头印的是"最近 10 条"。近期决策按 `ADR-` 后的**数值**排（文件名补零三位，字典序只是恰好在 999 张以内等于数值序）。

日期的**唯一读法**是 `_normalize_day()`：它同时吃 `2026-08-16` 与 `08-16` 两种写法，统一返回 `(年,月,日)`，认不出就返回 None 而不猜。**写侧（`short_date()` 用 `%m-%d`，没有年份）与读侧必须共用这一处** —— 两边各写一份时，生产者与消费者对不上，而错误是静默的：不报错、不崩溃、退出码正常，只有把产物打开看才会发现（`days_since` 曾因此对自己的产出恒返回 None，构思超期判定从未生效过一次）。缺的年份按「补出来若晚于今天就是去年」推断。

## 三、L2 决策卡（ADR）

**什么时候写**：出现下列任一即写，不写就别改。

- 在 A 与 B 之间选了一个（且 B 不是明显错的）
- 推翻了之前自己的定法
- 划了一条"不做的边界"
- 合并 / 废弃了一个已注册资产

**五字段**（模板 `references/templates/decision.md.tpl`）：

```markdown
# ADR-004 · 持仓卡片改为服务端排序

- 日期：2026-09-24
- 状态：生效（/ 被 ADR-009 取代）
- 影响资产：UI-012、API-003

## 背景
客户端排序在 500+ 持仓时掉帧。

## 决定
排序下移到 API-003，返回即有序。

## 备选与否决理由
- 虚拟列表：改不动现有滚动手势，成本高
- 分页：用户要一眼看全，否

## 如果错了会怎样
排序字段增加时 API 契约会变，需同步 UI-012。
```

最后一段「如果错了会怎样」是 ADR 里最被省略也最有用的一句——它让后人敢推翻你。

**取代不删除**：ADR-009 取代 ADR-004 时，把 004 状态改为「被 ADR-009 取代」，保留原文。删掉历史 = 下次又走一遍老路。

## 四、L1 会话记录

收工时写，五段，可短到三行（模板 `references/templates/session.md.tpl`）：

```markdown
# 2026-09-24 · 持仓卡片排序改造

## 本次目标
一句话。

## 做了什么
- （动过的资产 ID + 一句话）

## 结论
- 定下来的 / 否掉的

## 开环
- 未完成、卡在哪、下次从哪接

## 下次起步点
一句话，直接可执行。
```

**「下次起步点」必须有**。它是跨会话续接的关键——写下"下一步打开 UI-012 把 mock 换成真实 API-003"，比写"继续做排序"有用十倍。

## 五、开环（open-loops.md）

四列：事项 / 卡在哪 / 关联资产 / 登记日。每周清一次，能闭环的闭环，决定不做的显式标注「放弃 + 理由」并写决策卡。

**怎么写进去**：`close --opens` 用**竖线**分隔前三列，登记日自动填；第一段（事项）必填。

```bash
registry.py close --summary "排序改到服务端" --opens "等后端接口|卡在 API-003 未联调|UI-001"
registry.py close --summary "先只记事项"     --opens "确认目录层级"
```

超过三段直接报错、第一段为空也报错——**宁可拒绝，不写坏表行**。曾经把整串塞进「事项」列：用竖线补另外两列会写出 7 个竖线的坏行（4 列应为 5），读回时登记日被静默丢弃，而 `add` 是拒绝竖线的——同一个技能两套标准。`卡在哪 / 关联资产` 留空是允许的，但 `关联资产` 一空，`check` 就会报「开环没有归属资产」；写「无 / - / N/A」会被当空值处理（占位词不该骗开闸门）。

一次 `close` 登记**一条**开环（<code>--opens</code> 是单值）。要一次记多条，就分几次 `close`，或直接手改 `open-loops.md` 的四列表格——表结构与上面完全一致。

**开环不分档**：L / M / F 三档都有 `open-loops.md`，`close --opens` 一律入账，`loop --list/--done`、上下文包第 5 段、`check` 的开环闸门全部照常工作。曾经把它做成 M/F 专属，结果 L 档的 `--opens` 只以纯文本躺在 `log.md` 里——四个出口同时失明，而 L 档（资产<15 / 单人 / 短周期）恰恰是最需要"下次从哪接"的场景。**档位只简化目录结构，不砍能力。**

**闭环必须有动作**（只增不减是反面教材）：

```bash
registry.py loop --list          # 按阻塞程度列出，带编号
registry.py loop --done 3        # 闭环第 3 条（也可给关键词）
```

闭环的条目**移到 `## 已闭环` 段保留**，不删除——历史留着，`check` 与上下文包只统计未闭环的那部分。同一事项不会被重复追加（`reconcile --write` 反复跑也不会堆一批一样的条目）。

超过 15 条时 `check` 会强制提醒做一轮"放弃还是做"的裁决，别让它变成第二个垃圾场。

## 六、收工三步（硬闸门）

1. 写/追加会话记录（含"下次起步点"）
2. 更新本次动过的注册项状态（批量，不在中途改）
3. `registry.py close` → 刷新上下文包 + 把新开环写进 open-loops.md + **收工体检**

L 档第 3 步照样生效（流水写 `log.md`，上下文包从 `log.md` 切块生成，开环同样进 `open-loops.md`），不会因为档位轻就跳过。

### 收工体检（`close` 自带；只提示，不阻断）

收工是**反思时刻，不是审判时刻**。`close` 会多看两眼磁盘，把「登记了却没交代」的四类摆出来，并把结论写进会话记录的 `## 收工体检` 段（0 项时不占行，终端只打一行 `收工体检：0 项待交代 ✅`）：

| 类 | 判据 | 该怎么裁决 |
|---|---|---|
| 构思未落盘 | 状态 `构思`，位置没写或磁盘上没有 | 落盘就 `set --status 在建`；决定不做就写决策卡并 `retire` |
| 构思但其实已落盘 | 状态 `构思`，但位置底下已有扫描范围内的源码文件 | 状态没跟上：`set <ID> --status 在建` |
| 位置不存在 | 状态不是 `构思`，路径在磁盘上找不到 | 路径写错 / 文件被删。`check` 会报 ERROR，收工前清掉 |
| 未登记文件 | 在扫描范围内、却不被任何资产的「位置」覆盖 | 跑 `reconcile` 出完整提议；不登记的写决策卡说明为何不登记 |

**为什么不阻断**：四类里有两类（构思未落盘 / 构思但其实已落盘）是**顺序问题，不是错误**——把它们变成 ERROR 会让人不敢先登记。所以它只报数、给裁决建议，退出码永远是 0；`--no-doctor` 可跳过（不推荐：跳过就等于放弃收工时唯一那一眼磁盘对账）。

> 与 `check` 的分工：`check` 只看注册表内部一致性（快、可反复跑，ID / 状态 / 位置 / 决策引用 / 开环 / 依赖状态机；其中**悬空依赖默认只到 WARN**，要它卡人就显式加 `--strict-deps`）；体检要多看两眼磁盘（构思是不是其实已经落盘了、有没有绕过登记的新文件），那两眼都贵，所以只在收工时跑一次。另外文件归属**两处同口径**（最长「位置」胜）——早先 `reconcile` 是「先命中先返回」，嵌套位置下同一个文件可能被归给两个不同的资产。

**收工不沉淀 = 下次从零开始。** 允许会话记录只有三行，不允许没有。
