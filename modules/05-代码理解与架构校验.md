# 05 ｜ 代码理解（导入级）与架构校验

**上一步输入**：02 的注册表、04 的 manifest 出口已在跑。
**本步要做**：让机器能读代码库、并按**你声明的架构规则**判违规——不是"生成一张漂亮图"，是"这条依赖到底许不许"。
**输出给**：`audit` 报告 + 机器可读 JSON、`viz` 架构图（违规边标红）、`diff` 架构演进说明。

> **前置声明**：本模块仍是**零依赖**（纯 stdlib，不装语言服务器、不装 node）。
> 代价写在明处：理解只到**导入级**，不到符号级。详见下面「诚实边界」。

---

## 一、三件东西的分工（别混用）

| 命令 | 一句话 | 事实从哪来 | 产物 |
|---|---|---|---|
| `scan` | 读 src，解析 import，建**文件级**依赖图 | 正则扫源码 | `imports.json` / `imports.md` |
| `audit` | 拿依赖图**对照你的层间规则**判违规 | scan 的图，或注册表声明的依赖 | `architecture-audit.md` / `.json` |
| `diff` | 两份 manifest 对比，出架构演进 | 两次 `export` | `architecture-delta.md` / `.json` |

一句话记法：**`scan` 造事实 → `audit` 用法则 → `diff` 说变化**。`viz` 是它们共同的呈现端。

## 二、`scan` ｜ 导入级代码理解

```bash
registry.py scan [--ext .ts,.tsx] [--out <file>] [--json <file>] [--root <dir>]
```

产出四类东西，一次给全：

1. **文件级依赖边**：谁 import 谁，区分三种性质
   - `int` 项目内命中（解析到具体文件，或解析到目录——Go / Java 的包写法）
   - `ext` 外部依赖（`react`、`os`、`fmt`，按包名归一）
   - `unres` 像本地却没找到 → **值得看**，通常是路径写错或后缀不在扫描范围
2. **有效行数**（约）：去空行 / 行注释 / 块注释。多行字符串按注释处理，是近似值。
3. **增量缓存**：按 `(mtime, size)` 指纹复用上次解析（`.project/registry/.scan-cache.json`）。第二次跑同一批文件会报 `命中增量缓存 N`。
4. **声明依赖 vs 实际导入**（最有价值的一张表）
   - **漏声明**：代码里真导入了、注册表没写 → 优先看这批
   - **多声明**：注册表写了、代码里没看到导入 → 可能是合法的软依赖（事件总线、DI），也可能是过期条目
   - **位置对不上**：登记了「位置」但**磁盘上根本找不到那个路径** —— 路径写错 / 文件被删。**这是真问题。**
   - **非源码资产**：位置在磁盘上**存在**，只是后缀不在扫描范围（`.md` / `.tpl` / `.json`）—— **不参与对账，这不是问题。**
   - **构思中未落盘**：状态是 `构思`（开工前先登记）—— 位置只是**意向**，还没写。**这不是问题**，也不参与对账。
     另有一条「构思但已有源码文件」：位置底下已经扫到文件了，说明落了盘，`set <ID> --status 在建`。
     > 这三类**必须分开**。文档型项目（技能包 / 写作 / 调研）里 17 个资产可能有 16 个是 `.md`，若一并报成
     > 「位置对不上」，读者第一眼就把整段当废纸，而真幽灵正藏在这 16 条里。同理，「多声明」只在**两端都是源码资产**时统计：
     > 文档没有 `import` 可比，拿它比「代码里怎么没导入」命中率必然 100%。（技能自审时实测：改前 多声明 28 / 位置对不上 16，
     > 全是假信号；改后 0 / 0，非源码资产 16 单列。）
     > **构思这一类的教训**：它当初被四个出口（`check` / `context` / `reconcile` / `scan`）各报成一次问题，而「先登记再动手」正是本技能写死的默认顺序——第一步就撞上自己的闸门。豁免只给 `构思`；状态改成 `在建` 后四处立刻恢复报警（定向驱动带负向对照）。

### 支持的语言与解析写法

| 后缀 | 抓什么 |
|---|---|
| `.ts .tsx .js .jsx .mjs .cjs .vue .svelte` | `import ... from "x"`、`export ... from "x"`、`require("x")`、`import("x")`；相对路径按后缀表补齐（`./a` → `a.ts` / `a/index.ts`）；`@/` `~/` 当项目根相对 |
| `.py` | `import a.b`、`from a.b import c`、`from . import x`（点数决定上溯层数）、`__init__.py` |
| `.go` | `import "p"` 与 `import ( ... )` 块；包路径若能对上项目内目录则算内部 |
| `.java .kt .cs` | `import a.b.C;` / `using X.Y;` 点号转路径 |
| `.rs` | `use a::b`；`crate::` / `self::` / `super::` 算项目内 |
| `.rb .php` | `require "x"` / `use X\Y;` |

### 诚实边界（读这份报告时必须知道）

**这是导入级，不是符号级。** 正则法的固有代价，会漏也会误：

- **动态导入抓不到**：`eval`、`importlib.import_module`、`require(变量)`、`__import__`。
- **重导出与别名会误判**：`export * from` 链、tsconfig `paths` 别名（只认 `@/` `~/` 两种写法）会被归到外部。
- **条件导入**：`if TYPE_CHECKING:`、`try: import x except:` 一律当真实导入。
- **注释与字符串里的 import 会被误当真实导入**——正则不看上下文。
- **符号级信息（函数 / 类 / 引用 / 类型层级 / 谁调用了谁）本工具不产出**。要这些必须外接语言服务器（Serena），见 `modules/04`。
- **资源依赖看不见**：脚本读 `references/` 里的模板与类型定义、读某个 JSON 配置——这类**文件读取不是 import**，`scan` 一条都抓不到（技能自审时 `registry.py` 读 8 个资源文件，导入图上是 0 条边）。
- **信息量取决于项目类型**：知识型项目（技能包 / 文档 / 写作）里「项目内边」常常就是 **0**——架构活在文档与资源引用里，不活在 import 语句里。此时架构判断走 `audit --source registry`（手写依赖），**别把「0 条边」读成「架构很干净」**。

一句话：它能告诉你**「这层碰了那层」**，不能告诉你**「这个函数调了那个函数」**——也告诉不了你**「这份文档引用了那份文档」**。

### 增量扫描的注意点

缓存键是 `(mtime, size)`。如果一次编辑**没改变字节数**（同名替换、改一个字符），mtime 变了所以会重解析——安全。但**用 `cp -p` / 解压覆盖保持原 mtime** 时会命中旧缓存，此时删 `.scan-cache.json` 重跑。

## 三、`audit` ｜ 声明式架构校验

```bash
registry.py audit --init                                   # 生成规则骨架
registry.py audit [--config <file>] [--source auto|imports|registry]
                  [--ext ...] [--strict] [--out <file>] [--json <file>]
```

### 规则文件 `.project/architecture.json`

```jsonc
{
  "schema": "project-registry/architecture@1",
  "default": "allow",                       // 没有规则命中时怎么办：allow | deny
  "layers": [                               // 路径 → 层
    { "name": "ui",  "paths": ["src/ui/**"] },
    { "name": "api", "paths": ["src/api/**"] },
    { "name": "data","paths": ["src/data/**"] }
  ],
  "rules": [                                // 允许 / 禁止的层间边
    { "from": "ui",  "to": "ui",  "allow": true  },
    { "from": "ui",  "to": "api", "allow": false },   // ← 这一条才是「违规」的来源
    { "from": "api", "to": "data","allow": true  },
    { "from": "*",   "to": "*",   "allow": true  }    // 兜底
  ],
  "maxFanout": 8                            // 单个文件依赖目标数上限（0 = 不检查）
}
```

**匹配语义（必须记住这一条）**：`rules` **按顺序匹配，第一条命中生效**。
所以写法是 **先写例外、后写总则**。反了就会得到一个「所有边都被允许」的规则表却自以为在管架构。

- `from` / `to` 可以是**层名**、`*`、或**资产 ID glob**（`UI-*`，只在 `--source registry` 下有对象可匹配）。
- `to` 可以是数组：`"to": ["api", "util"]` 表示这两个都按这条算。
- 路径 glob：`**` 跨目录，`*` / `?` 不跨目录；`src/ui/**` 同时匹配 `src/ui`（目录本身）与 `src/ui/...`——资产的「位置」是目录，需要这一条才认得出来。
- 一个路径命中多个层时，取**最长匹配的那条规则**（最具体的 glob 胜），同长取配置靠前的。

`--init` 生成的是「所有目录各一层 + 一条全允许」，**它默认不报任何违规**——规则要你自己收紧。
`--init` 不会覆盖已有文件（要覆盖加 `--force`）。

### 六类判定

| kind | 含义 | 哪个事实源会产出 | 严重度 |
|---|---|---|---|
| `layer` | 规则拒绝的依赖边（层间违规 / 资产间违规） | 两者 | 高 |
| `cycle` | 循环依赖（导入模式下是**文件级**，注册表模式下是声明依赖级） | 两者 | 高 |
| `fanout` | 单点依赖目标数 > `maxFanout` | 两者 | 中 |
| `unassigned` | 文件不属于任何已配置的层（规则管不到它） | 仅 `imports` | 中 |
| `unresolved` | 相对导入解析不到目标 | 仅 `imports` | 低 |
| `ghost` | 登记了「位置」但扫不到文件（**`构思` 状态豁免**：位置是意向，还没落盘） | 仅 `imports` | 低 |

后三类**只在导入级事实源下产出**（`registry` 源没有文件级信息，报不出来），
所以换 `--source` 时报告会少三段——那是预期的，不是坏了（报告末尾的判据说明会自己写明）。

`fanout` 的**算法与 `graph` / `viz` 的「上帝资产」共用一套**（`_fanout_map`：目标含悬空引用、
去重、排除自环），只有**阈值**不同：这里用 `maxFanout`，那两个用 `GOD_FANOUT = 5`。
所以「换个命令就换个出度」这类事不会再发生，剩下的差异只来自阈值。

### 事实来源两种，行为要一致

- `--source auto`（默认）/ `imports`：用 `scan` 的导入图 → **文件级**违规。
- `--source registry`：用注册表声明的 `依赖` → **资产级**违规。想先管住"人写的架构意图"用这个；想抓"代码实际长成什么"用上面那个。
  > 它的质量前提是 `依赖` 列可信，所以 `add` / `set --deps` 有**写入时闸门**：引用了未登记的 ID 直接拒写（rc=2），
  > `--allow-dangling-deps` 才放行。悬空边一旦进了表，`--source registry` 的违规判定与出度都会跟着偏
  > （`scan` 一侧另有「悬空引用」段独立报出）。存量用 `check --strict-deps` 清。
- 两者都会报 `cycle`：同一个事实只在一侧算，会出现"换个 source 就换个结论"。

### `--strict` 接 CI

默认 `audit` 有违规也返回 0（只出报告）。加 `--strict` 后 **有 `layer` / `cycle` / `fanout` 任一违规就退出码 3**。
把 `registry.py audit --strict` 放进 CI 或收工脚本，架构约束才算真的"闸门"，否则只是一份文档。

### 两个出口要一起指定（踩过的坑）

`audit` 的 `--out`（md）和 `--json`（机器读）是**两个独立选项**，`--json` 默认落
`<项目根>/.project/registry/architecture-audit.json`。所以**做反向对照实验**（拿一份故意写错的配置验证闸门会不会响）时，
只把 `--out` 指到临时目录、漏了 `--json`，对照组的结果会**覆盖真产物**。
规矩：对照实验两个出口都显式指定，跑完把真产物再生成一次。

## 四、`diff` ｜ 架构演进（带机器收据）

```bash
registry.py diff <base-manifest.json> <head-manifest.json> [--out <file>] [--json <file>]
```

四类差异 + 决策变化：

| 类 | 判据 |
|---|---|
| **新增** | head 有、base 没有的资产 |
| **移除** | base 有、head 没有的资产 |
| **变更** | 同名资产的字段差异（语义名 / 状态 / 依赖 / 别名 / 位置 / 决策） |
| **移动** | 位置变化（**变更的子集，单独列出**）——重构最常发生的事 |
| 决策 | 新增 / 移除 / 状态变化（ADR 生效→作废等） |

**机器收据**：报告头部带三个哈希——`base` 指纹、`head` 指纹、`delta` 收据。
收据哈希**只由两端资产指纹与计数决定：不含时间戳，也不含 manifest 的文件名**。

第三条是踩出来的：早先连文件名一起哈希，而本文档自己推荐的基线名就是
`baseline-<日期>.json`——下周导出换个名字、架构一个字没动，收据也会变，
「过一周再跑、收据没变＝架构没动」这条用法**天然失效**。现在保证：
**同内容必得同收据，无论文件叫什么、放在哪**；内容真变了（哪怕只改一个资产的状态）收据必变。

用法：把它写进 PR 描述或评审记录，就是「这一刻的架构」的可核验凭证。
（报告里仍会如实写出两个 manifest 的文件名——那是给人看的信息，不参与哈希。）

`diff` 不需要 `.project/`，可以在任何目录对两份 JSON 跑；坏输入（非法 JSON / 缺文件）会**友好拒绝**，不是甩一个 Python 栈。

## 五、`viz` 上的联动

`viz` 渲染时会自动读 `.project/architecture.json`：

- 违规的依赖边画成**深红实线**（与「环 / 幽灵」的浅红虚线区分开）
- 统计徽章多一格 **层间违规**
- 明细区列出违规的**资产对**，鼠标悬停 `code` 显示证据（哪个文件里的哪条 import）

**为什么要"翻译"**：`viz` 画的是注册表资产（`UI-001`），`audit` 判的是文件路径（`src/ui/card.ts`）——同一个事实两套名字。所以 `viz` 会把文件级违规映射回资产级边再上色；映射不上的（发生在未登记文件之间）会在终端明确告诉你「N 条图上无对应边」，**不静默吞掉**。
没配置 `architecture.json` 时徽章显示 `—`，并在终端提示 `audit --init`。

**违规边即使注册表没声明也会画出来**。最危险的违规恰恰是「代码里有、注册表没声明」的那些（它们同时也是 `scan` 报的"漏声明"）；只在已声明的边上标红，等于在最该报警的时候一根红边都没有。这类边另用一段浅黄底说明「只存在于代码里」，**并且不计入「依赖边」徽章**——那个数要和 `graph` 报的是同一个值。

**两个「循环依赖」不是一回事，别当成矛盾**：`viz` / `graph` 报的是**注册表声明的依赖**有没有环；`audit --source imports` 报的是**代码文件级**的环。声明是对的（无环）而代码里绕回来了，是完全正常的一种状态——那正是 `audit` 存在的理由。

**「上帝资产」与「出度超限」：同一套算法，两个阈值。** 算法单点定义在 `_fanout_map`——
目标**含悬空引用**（声明了 6 个就是 6 个，其中一个 ID 写错不代表只依赖 5 个；而且"有悬空引用"
正是 `graph` 自己要报警的状态，此时两个出口最该一致）、**去重**（同一个 ID 写两遍不算两个）、
**排除自环**（那是 `find_cycles` 的事）。早先 `graph` 与 `viz` 各写一遍、口径还不一样，
于是同一个项目的同一个体检项会报出两个数（实测 UI-001 一处报 1、一处报 0）——现在两边同源。

阈值仍有两个，这是**有意的**：`graph` / `viz` 的「上帝资产」用硬编码的 `GOD_FANOUT = 5`
（经验值：超过 5 个就该想拆），`audit` 的「出度超限」用 `maxFanout`（骨架 8，可配可关）。
所以一个出度 6 的资产会同时是 `viz` 的「上帝资产」和 `audit` 的「不算超限」。两个数都没错——
**引用读数时带上阈值**，并且把「算法口径」和「阈值口径」分开说，别混为一谈。
还有一个判据上的坑：**索引型资产**（入口文件、能力清单、工具脚本读的资源表）出度天生高——它扇出到子件是它的形状，不是它的病。判"上帝资产"要先问一句：高 fan-out 是"什么都往这儿挂"，还是"它就是那张目录"。

**跨列长边会走行间通道**：一条边如果跨了 2 列以上，直接画横向曲线会从中间那个方框**背后穿过**，看起来像连到了错误的节点。所以这类边改道到「本行下方的行间通道」（行距 64 / 框高 46 → 通道净高 18，横向全程无遮挡；垂直下潜段落在两列之间 44px 的空档里）。相邻列的边仍走原来的贝塞尔。

## 六、判据说明（别误读报告）

- **层间违规是结构性判断，不是 bug 清单。** 有些跨层依赖是刻意的（DI 容器、事件总线、共享类型包）。规则表是你的**架构意图**，报告是"代码与意图的差"，不是"错误列表"。
- `from` 是依赖者、`to` 是被依赖者。违规 = 规则拒绝这条边。
- **事实取决于 `--source`**：`imports` 是**导入级**的（既可能漏报——动态导入看不见，也可能误报——注释里的 import、别名没配）；`registry` 是**人写的声明**（代码里真实存在、注册表没登记的边不在报告里，那类要靠 `scan` 的对账段查）。
- **导入级的信息量取决于项目类型**：代码型项目吃得到；知识型项目（技能包 / 文档 / 写作）常见「文件 1 / 边 0」——此时必须走 `--source registry`，否则"0 违规"只等于"没东西可查"。
- 想改判就改 `rules`（先例外后总则）再重跑；想改事实就修代码或补 `--ext`。
- **层间违规有两个读数，不是两个 bug。** `viz` 与 `audit` 同源同单位（都折算到「资产级边」，
  共用 `violations_both_sources` 一次算出），但它们报的是**两个不同的事实源**：一个吃注册表声明的
  依赖，一个吃代码里真实解析出的导入。**两个数不相等是正常的**（相等才说明两边已同步）。
  徽章会同时写出 `N 声明 / M 导入`，`audit` 报告的「1b 折算到资产级」段给出**同一对数**——
  拿 CLI 去比页面，两边必然一致。
  > 早先只报一个数（导入源的投影），用户拿它去比 `audit --source registry` 永远对不上，还以为是
  > 「同一事实算了两遍打架」。修法不是强行让两个数相等（那会把真实差异抹平），而是**把两个数都摆出来**。
- 除此之外，单源内部的数（同一事实源的徽章 / 明细 / CLI 打印）来自**同一次计算**，不会互相打架。

## 七、与外部工具的分界

| 能力档 | 归谁 | 为什么 |
|---|---|---|
| **导入级**依赖与违规 | **本技能（已内置）** | 零依赖、可离线、够回答"这层碰了那层没有" |
| **符号级**理解（函数/类/引用/类型层级） | Serena（MCP + LSP，可选） | 需要语言服务器，40+ 语言按语言另装依赖 |
| 多视图渲染（时序 / 工作流 / 数据流 / 生命周期） | Archify 等外部画图技能（可选） | 本技能只有架构图一种视图 |

**不要指望 `scan` 干 Serena 的活，也不要指望 `audit` 干 Archify 的活。** 分工的理由与接入协议见 `modules/04`。

### 三档事实的粒度对照（**唯一权威表**，别在别处复述）

| 来源 | 粒度 | 依赖谁 | 能回答 |
|---|---|---|---|
| `reconcile` | **文件级** | 零 | 这个东西**在不在**注册表里（未登记 / 失效登记 / 命名违规 / 疑重） |
| `scan` | **导入级** | 零 | 谁 import 谁、跨文件跨目录的实际依赖、有效行数 |
| Serena | **符号级** | MCP + LSP | 这个**函数 / 类 / 变量**被谁引用、类型层级、跨文件重命名 |

三档是**精度递增**，不是替代关系：文件级能抓「偷偷加了个文件」，导入级能抓「这层碰了那层」，
符号级才能抓「这个函数被 7 个地方调用，改它要动 7 处」。`reconcile` 与 `scan` 都
**不读语义、不建 AST**，所以永远给不出符号级答案——那是语言服务器的活。

> 这张表原先在 `modules/04` §二 也有一份（同一件事写两处）。ADR-002 决定：**04 缩成接入协议 + manifest schema**，
> 机制说明只留 05。**两边冲突时以本节为准**。
