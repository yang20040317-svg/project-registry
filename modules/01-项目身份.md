# 01 ｜ 项目身份（PROJECT.md）

**上一步输入**：用户说"我要做个 X 项目" / 已有一个混乱的项目要接管。
**本步要做**：把项目变成一张可引用的卡——它叫什么、是什么类型、多大规模、现在什么阶段、不做什么。
**输出给**：02 命名注册表（决定资产维度）、03 记忆层（决定上下文包的第一段）。

---

## 一、身份卡六字段

`.project/PROJECT.md` 只需六个字段，缺一不可：

| 字段 | 写什么 | 反例（不合格） |
|---|---|---|
| **一句话定位** | 这个项目给谁、解决什么。"给独立开发者管理多项目的资产与决策台账" | "一个管理系统"（没说给谁、解决什么） |
| **项目类型** | `code-ui` / `writing-content` / `research` / `custom`，可多填 | 空着（维度无从路由） |
| **规模档位** | `L` / `M` / `F` | 一上来就 F（管理成本压死项目） |
| **当前阶段** | 一句话 + 日期。"原型验证中（09-24）：三个核心 UI 已可用" | "进行中" |
| **边界（不做什么）** | 显式列出 3 条以内的"本项目不做" | 不写（范围会自己长大） |
| **验收信号** | 怎样算这个阶段成了，可观察 | "做好了"（不可观察） |

模板：`references/templates/PROJECT.md.tpl`

---

## 二、类型选定（决定资产维度）

按顺序判定，命中即停：

1. 主要产出是**可运行的东西**（代码 / 界面 / 接口）→ `code-ui`
2. 主要产出是**可读的东西**（文章 / 书 / 剧本 / 内容站）→ `writing-content`
3. 主要产出是**一个结论**（调研 / 分析 / 实验 / 竞品研究）→ `research`
4. **混合型**：`init --type "code-ui+writing-content"`（`/` `,` `&` 也认）。两型维度取**并集**、同前缀去重，同时用 `UI-` 与 `CH-` 前缀。写错的类型名会打印「未识别的类型 X」而不是被静默吞成单一 `ITEM` 分节——发生这种情况用 `--dims "PFX:名称"` 补上。
5. **都不像** → `custom`，按 `references/project-types/custom.md` 的维度三问自造。

> **不要为了通用而造抽象维度**。能用现成四类就别 custom；custom 是兜底不是默认。

---

## 三、规模分档（管理不许比项目还重）

| 档 | 判据 | 落盘 |
|---|---|---|
| L | 资产 < 15 且 单人 且 预期 < 2 周 | PROJECT.md + index.md + memory/log.md + **open-loops.md + context-packet.md** |
| M | 其余（**默认**） | 同上，但拆开 sessions/ 与 decisions/，不再混记 |
| F | 资产 > 50 或 多人协作 或 预期 > 3 个月 | + `entities/`（`add` 时自动开详卡）+ `dependencies.md`（`graph` 生成） |

**档位只简化目录结构，不砍能力**：开环与上下文包三档全给。曾经把 open-loops.md 划给 M/F，结果 L 档的 `close --opens` 只以纯文本躺在 log.md 里，`loop --list`、上下文包第 5 段、`check` 的开环闸门四处同时失明——而 L 档恰恰最需要"下次从哪接"。

**升档不补历史**：从 L 升 M 时，不必把 log.md 拆回 sessions/；从当天起用新结构即可，log.md 标注「历史归档」。

## 四、接管既有项目（比新建更常见）

项目已经臃肿了才来找本技能时，走**盘点四步**，不要一次性完美登记：

1. **扫**：列出实际存在的顶层单元（目录 / 主要文件 / 主要产出物）。不读全部代码，只认"单元"。
2. **粗登**：给每个单元一个 ID + 语义名，**允许语义名暂时含糊**，状态统一记 `在建`。
3. **标疑**：凡"看起来和另一个是一回事"的，登记为**疑重**，写进 `open-loops.md`，不当场合并。
4. **逐轮收敛**：后续每次开工处理 1–2 个疑重，处理完写决策卡说明"合并 / 保留两个 / 废弃其一"。

> 接管期铁律：**先粗登全覆盖，再逐步精确**。追求一次登记完美 = 永远登不完 = 技能失效。

### 落盘参数（接管时尤其要看清）

| 参数 | 行为 |
|---|---|
| `init`（默认） | `.project` 已存在就报错退出，**绝不覆盖** |
| `--force` | 重建骨架：先备份到 `.project.bak-<时间戳>`，`memory/` **一个字不动**，既有资产行**原样迁回**新 index.md |
| `--force --reset` | 才真正清空（含 `memory/`），同样先备份到 `.project.bak-reset-<时间戳>` |
| `--dims "UI:界面元素,MOD:功能模块"` | **补充**维度：与类型维度**合并**（同前缀去重，同前缀以 `--dims` 的标题为准），不是替换。类型是 `custom` 且 `--dims` 也没给有效前缀时只给通用 `ITEM` 分节——不会拿文档里的示例行当前缀（那会产出 `## ... (XXX)` 这种垃圾分节） |

> **`--force` 只重建骨架，不清账本。** 接管既有项目时误加一次 `--force` 就把开环与资产全清掉，是这套机制最不该有的失败模式。

> **并发写是安全的。** 所有写命令（`init` / `add` / `set` / `retire` / `close` / `loop --done` / `idseq --set` / `reconcile --write`）会在 `<项目根>/.project.lock` 上取互斥锁，「读 → 改 → 写」是一个事务。两个终端同时 `add` 不会再各发一次 `UI-001`，也不会互相覆盖；等不到锁（默认 20 秒）会**直接报错**而不是偷偷写坏。`.lock` 是个常驻的 1 字节文件（建议随项目一起提交），锁由**操作系统**持有：进程正常结束或崩溃都会自动释放，不需要手动清理，也不存在「残留死锁」。
