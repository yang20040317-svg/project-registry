## 一、ID 规则（机器键）

```
<PREFIX>-<NNN>      例：UI-012、CH-003、ADR-007
```

- **PREFIX**：2–4 个大写字母，来自所选类型的维度定义（`references/project-types/`）。
- **NNN**：三位序号，**全局单调递增，永不回收**。废弃的 ID 留着标 `废弃`，回收会让历史记录指向错的东西。

> **内置维度表按项目类型取用**：单一类型的项目只认自己那一张——`research` 项目里 `UI` 不算数，因为它是 `code-ui` 的前缀；四条边界一次说清：
> ① `index.md` 里建过节的永远合法，这条优先级最高，所以老项目零影响；
> ② `custom` / 混合类型 / 类型未标注或未识别 → 保留四张表的并集（`custom` 恰恰是最需要那张参考表的人，混合类型的前缀空间本就设计为共享）；
> ③ 真要借用别家前缀 → `add --type UI --dims "UI:界面件"`，显式声明并写进 `naming.md` §四；
> ④ 类型解析必须复用 `split_types()` 与 `init` 那套口径——两边一分岔就会出现「`init` 建了节、`add` 判它非法」。

**「永不回收」靠游标，不靠文本扫描**：`add` 发号取 `max(现存行, .idseq.json 游标) + 1`，游标只在真正发号时前进，删行不回退——所以删掉末位那一行，新资产也拿不到同一个号。

> **为什么文本里出现过的号不再参与发号**：曾经把「`.project/` 全文扫到的最大号」也算进基数，结果依赖列手滑写一个 `UI-999`，下一条就发成 `UI-1000`，游标被写成 `{"UI":1000}` 且不可逆。讽刺的是同一次 `check` 明明已报「引用了未登记的 UI-999」——脚本知道那是笔误，却拿它当"该号用过"。
> 冷启动例外：游标缺失时（老项目 / 手删了 `.idseq.json`）才扫文本做一次性推断，且**孤立引用不计入**——同一号要在 ≥2 个文件里出现才算真发过。之后一律以游标为准。

**游标要显式改动**用 `registry.py idseq`：

```bash
registry.py idseq                  # 看：前缀 / 游标 / 现存最大 / 下一个
registry.py idseq --set UI 3       # 改：只在确认某号真发过、或已废弃需永久保号时才上调
```

下调到现存最大号以下会被拒绝（那正是"回收"）。

**唯一例外**：`init --force --reset` 会连 `.idseq.json` 一起删，游标归零后旧 ID 可能被复用。这是底线唯一被打破的地方——命令会先打印警告并留 `.project.bak-reset-<时间戳>`。要保号：用不带 `--reset` 的 `--force`，或 reset 后用 `idseq --set <前缀> <原最大号>` 补回。
- ID **只做键，不承载语义**。语义交给"语义名"字段。别搞 `UI-PositionCard-New2` 这种把语义塞进 ID 的做法——那正是项目变臃肿的起点。

**一个资产 = 一行**。总表 `registry/index.md` 按类型分节：

```markdown
## 界面组件 (UI)

| ID | 语义名 | 别名 | 位置 | 状态 | 依赖 | 决策 | 更新 |
|---|---|---|---|---|---|---|---|
| UI-012 | 持仓资产卡片 | 资产卡/position card | src/components/AssetCard.tsx | 可用 | API-003 | ADR-004 | 09-24 |
```

## 二、命名三问（发 ID 前必须答出）

1. **它是什么**：一句话职责，动词开头优先。"展示单个持仓的市值与涨跌"。
2. **它和邻居的边界**：与最像的那个资产差在哪。"只管展示，不管交易下单（那是 UI-015 的事）"。
   答不出这条 → 说明它很可能就是那个邻居，走查重。
3. **怎么称呼它**：语义名，写给三个月后的自己看。

### 禁用词（见到就打回）

| 禁用 | 触发条件 | 为什么 |
|---|---|---|
| 新的 / 新版 / New / v2 / 最终版 | **出现在任何位置**（做定语也算） | 时间词不是语义，三个月后全是"新版" |
| 临时 / temp / tmp | **出现在任何位置** | 临时的东西最终都会变成正式的 |
| 优化 / 改进 / 增强 | 单独使用 | 相对什么优化？ |
| 管理器 / Manager / Helper / Utils | **无修饰**（去掉它就没内容） | 等于没说是什么 |
| 模块 / 组件 / 测试 | 单独使用 | 类型词不是名字 |

两档的区别是**脚本实现也是这么分的**，别把它们混成一档：

- 时间词与"临时"做定语同样是反模式 → `新的持仓卡片`、`临时缓存` 都拦。
- 类型词与"优化"做后缀是正常的 → `持仓模块`、`性能优化`、`PositionManager`、`行情 Manager` **都放行**；只有光秃秃的 `模块`、`Manager`、`测试` 才打回。

> 曾经把 `模块 / Manager / 优化` 当子串禁用，结果 `性能优化` 和 `行情 Manager` 被误拦——而文档写的是"无修饰 / 单独使用"。**文档写了条件，代码就得按条件判**，否则闸门一边放跑真违规、一边拦住正常命名，人很快就学会无视它。

**这是闸门不是提示**：`add` 命中即退出（exit 2），给出改写要求；确属例外才 `--force`，并在决策卡写明为什么必须用这个词。

**版本演进用状态与决策表达，不用名字表达。** 要替换 UI-012 → 新发 UI-031，UI-012 标 `废弃`，决策卡写清为什么换。

## 三、查重三查（命名闸门的核心）

新建前**必须**依次过三查，任一命中 → 不新发 ID：

1. **同名查**：字面相同或仅差空格/大小写/中英文 → 直接复用。
2. **同义查**：查 `别名` 列与语义近似。"持仓卡片" ≈ "资产卡" ≈ "position card"。
3. **同职责查**（最关键）：名字完全不同但**做的事一样**。这查的是职责句，不是名字。
   - 判据：把两个资产的职责句并排，能不能说出"什么时候用 A、什么时候用 B"？说不出 → 重复。

命中后的三条出路（选一，并写进决策卡）：

| 出路 | 何时 |
|---|---|
| **复用已有** | 东西本来就够用，只是没找到 → 更新它，不新建 |
| **合并** | 两个都在用且职责重叠 → 保留一个，另一个标 `废弃` 并迁引用 |
| **显式另起** | 确有本质差异 → 新发 ID，且**必须在决策卡里写清"与 X 的差异"** |

> 脚本辅助：`registry.py find "持仓卡片"` 做同名/同义检索；同职责查需要你读职责句判断，脚本代劳不了。

## 四、状态机（五态）

```
构思 → 在建 → 可用 → 冻结 → 废弃
              ↘ 在建（改需求）
```

| 状态 | 含义 | 允许被依赖 | `check` 的反应 |
|---|---|---|---|
| 构思 | 只有想法，还没落盘（位置是**意向**，豁免路径校验） | ❌ | `WARN` 依赖了还在构思的 X（上游没落盘，这条依赖现在是空的） |
| 在建 | 正在做，结构未稳 | ⚠️ 可接受，但要在开环里标注 | 不报（提醒挂在开环里，不挂 check） |
| 可用 | 完成可用 | ✅ | 不报 |
| 冻结 | 完成但不再改动（稳定契约 / 已交付章节） | ✅ | 不报 |
| 废弃 | 不再使用，保留记录 | ❌ | `ERROR` 依赖了已废弃的 X（依赖链断了，改指新资产或写决策卡说明） |

「允许被依赖」列的 ❌ 由 `registry.py check` 执行——**表里画了叉，脚本就得真的卡住**；只写文档不落闸门，等于给状态机配了个装饰品（曾经废弃资产被依赖时 check 是 0 错 0 警）。`check` 有 ERROR 时退出码 1，收工前必须清掉。

### 构思 = 开工前登记的专用状态

它写下的「位置」是**意向位置**，还没落盘。所以四个出口一致地对它豁免路径类校验：

| 出口 | 对「构思 + 位置未落盘」的行为 |
|---|---|
| `check` | 不报 ERROR，末尾报一行 `PLAN 构思中 N 个未落盘（位置是意向，不做路径校验）`；汇总行带 `构思未落盘 N`；**挂超阈值的升为 `WARN 构思超期未落盘`**（仍不进 ERROR） |
| `context` | 第 3 段在活跃资产之后单列「**构思中（待落盘）N 个**」表；活跃为空时写「（无在建 / 可用资产）」而不是「无活跃资产」；第 6 段起步点提示「构思中的先落盘再动手」 |
| `reconcile` | 不算「失效登记」，第 2 段上方注明跳过了几个；终端摘要带 `构思跳过 N` |
| `scan` | 不算「位置对不上」，单列「构思中未落盘」段；位置已有源码文件的另报「构思但已有源码文件（状态该更新了）」 |

**只有构思享受这个豁免。** 状态一旦改成 `在建` / `可用`，四处立刻恢复照旧报警——否则这就不是「豁免构思」，而是「把四条闸门一起关掉」（定向驱动带负向对照：落盘后四处必须重新亮红）。

开工前登记的正规写法：

```bash
registry.py add --type UI --name "总览面板" --status 构思 --path "src/ui/overview"   # 位置还没建，先占号
registry.py add --type MOD --name "计分引擎" --status 构思                            # 位置也没想好，--path 不写
# …动手、落盘…
registry.py set UI-001 --path "src/ui/overview" --status 在建                        # 落盘即改状态
```

> 为什么会专门定这条：这四处曾经**各报一次**（`check` 报「位置不存在」把收工卡死、`context` 第 3 段按在建/可用过滤导致「开工第一读」恰好是空的、`reconcile` 报「失效登记」、`scan` 报「登记的东西不见了」），根因是只有 `check` 的**依赖闸门**认识「构思」。而「先登记再动手」正是本技能写死的默认顺序——等于让你在第一步就撞上自己的闸门。

### 构思挂多久算超期

「豁免」和「不追问」是两件事：豁免让它不挡路，超期升级负责不让它悄悄烂掉。
阈值三个来源，**就近优先**：

| 来源 | 写法 | 作用域 |
|---|---|---|
| 命令行 | `check --idea-days 3` | 本次调用 |
| 项目 | `PROJECT.md` 的 `- 构思超期阈值：7 天` | 这个项目（`init` 骨架自带 7 天） |
| 内置 | `IDEA_STALE_DAYS = 7` | 老项目没那行时兜底 |

`0` = 关闭超期升级（只保留 PLAN 提示行）。年龄按注册表**「更新」列**算——也就是「最后一次碰它的日期」，语义是**多久没人理它**，不是「登记至今多久」（后者要靠新字段，为一条提示改表结构不划算）。日期认不出来时**不报**：把「不知道」当「刚碰过」会让检查静默失效，比不报更糟。

> 这条判据曾**整条失效过**：「更新」列写的是 `%m-%d`（`09-25`，无年份），而 `days_since` 当时只认 `%Y-%m-%d` → 对自己写出来的值恒返回 None → 「构思超期」从加上那天起一次没响过。现在日期统一走 `_normalize_day()`（两种写法都吃，缺年份按「补出来若晚于今天就是去年」推断），**写侧与读侧共用一处**。教训记在 `modules/03`。

**只升 WARN、不进 ERROR**：今天登记、几天后动手是常态，卡住它会逼人不敢登记——那正好毁掉「先登记再动手」这件事本身。真要拦人，把 `check` + `audit --strict` 挂进 CI。

**状态只在收工时批量更新**，不在对话中途随手改——中途改 = 表永远不准。

走状态机的命令（ID 永远不变）：

```bash
registry.py set UI-012 --status 可用
registry.py set CH-003 --alias "第一章" --path "chapters/01.md"
registry.py retire UI-009 --reason "被 UI-031 取代，见 ADR-014"
```

`retire` = 状态置 `废弃` + 把原因追加进 F 档详卡的变更记录。**ID 仍然保留**，历史引用继续指向它——想彻底替掉就新发 ID 并写决策卡，不要复用旧号。

## 五、别名收敛

别名**只写在 `registry/index.md` 的「别名」列**——单一事实源。`naming.md` 里**不再抄第二份表**：两处必然漂移，抄一次就再也同步不上。

维护动作：

```bash
registry.py set UI-012 --alias "持仓卡/资产卡/position card/那个小卡片"
registry.py find "那个小卡片"      # 反查正式 ID
```

**维护时机**：每次发现一个新叫法就补进去。这是"记得住名字"最便宜的投资。

> 字段里**不许出现竖线 `|`**（会撑破 markdown 表格）与换行。`add` / `set` 会直接拒绝并提示改用斜杠、顿号分隔——静默接受一个坏字段比拒绝更糟。

同时记录本项目的**命名约定**（否则前后不一致）：

- 中文语义名 / 英文语义名是否都要？
- 代码标识符用什么风格（PascalCase / kebab-case）？与语义名如何对应？
- 简称规则（"用户持仓模块"可简称"持仓模块"，不可简称"用户模块"）

## 六、依赖与引用

- `依赖` 列填**资产 ID**，不填文件路径。路径会变，ID 不会。
- 循环依赖：两个资产互相依赖 → 说明边界划错了，写决策卡拆分，不要硬记。
- 依赖数 > 5（`GOD_FANOUT`）的资产：是"上帝资产"信号，进 `open-loops.md` 待拆。
  口径：目标**含悬空引用**、**去重**、**不含自环**；`graph` / `viz` / `audit` 三处共用同一算法，
  只是阈值不同（`GOD_FANOUT = 5` vs 规则里的 `maxFanout`）。引用读数时带上阈值。
- 这张依赖表能直接画出来：`graph` 出 mermaid 进 `dependencies.md`（带内容指纹，注册表一改就报过期）；
  **`viz` 出自包含 HTML 进 `registry/architecture.html`**——零依赖、单文件、双击即开，能按状态过滤、
  点节点看它的上下游。**先看四个数**：循环依赖 / 上帝资产 / 悬空引用 / 被依赖最多（改动成本最高）。
  这四个数是同一套判据，`viz` 与 `graph` 报的一定是同一个值。

**依赖必须指向已登记的 ID —— 这是写入时闸门，不是收工时的一句提醒。**

```bash
registry.py set UI-001 --deps API-777     # API-777 没登记
依赖闸门：依赖必须指向已登记的 ID —— API-777 还没登记。      # rc=2，没写进去
  API-777 未登记。是不是想写 API-001？
```

- 覆盖 `add --deps` 与 `set --deps`，**只校验本次要写入的值**：改状态、改名字不会被历史遗留的
  悬空依赖卡住（存量由 `check --strict-deps` 单独清账，见下）。
- 想依赖还没动手的东西 → **先把它登记成 `构思`**（已登记就不拦）。这条闸门顺带把「先登记再动手」
  又压实一步：想依赖什么，就先登记什么。
- 例外出口 `--allow-dangling-deps`：批量登记里的**前向引用**、以及有意造悬空边的**测试夹具**。
  放行时会回显放行了哪几条、以及留悬空边会污染哪三个出口（不会静默放过去）。
- 存量怎么清：`check --strict-deps` 把「依赖了未登记的 ID」从 WARN 升成 ERROR（rc=1），
  **默认口径一字未改**——它只做重新分级，不新增检查。
- 依赖了 `废弃` 的资产是**另一件事**：那是 ERROR（依赖链断了），在 `check` 里，不在写入闸门里。

**代码里的真实依赖是另一件事**：`依赖` 列是**人声明的意图**，代码里 `import` 出什么是**事实**。
对账用 `scan`（导入级，产出「漏声明 / 多声明」），判「这条依赖到底许不许」用 `audit`（层间规则写在 `.project/architecture.json`），看「这段时间架构变了什么」用 `diff`（带机器收据）。
两边不一致时**别急着改注册表**——先判断哪边才是对的（意图变了，还是代码跑偏了），判断完写 ADR。
详见 `modules/05-代码理解与架构校验.md`。
